# 产品/功能语言,非代码语言

跟用户讨论方案、问题、流程、人机交互时,**用产品语言和功能语言,不要用代码语言**。

## 必须避免的"代码语言"形态

- 代码块(用 ``` 把规则、方案、清单包成 code block)
- 函数名 / 路径 / 文件后缀名(`some_func()`, `src/foo.py`, `.ts/.py`)
- 工程师术语(hook、schema、API、interface、middleware、CRUD、JSON、payload、handler、wrapper、stub、mock)
- 提交哈希、变量名、行号
- 把规则或决策表达成代码片段而不是自然语言句子

## 应该用的"产品/功能语言"形态

- 描述功能行为(动词 + 受词):"加一个邮箱登录方式"、"框架自动贴一张纸条"、"工具拒收"
- 比喻和角色化:"门卫"、"管线"、"纸条"、"接管点"、"入口"
- 项目内已建立的概念词(议题 #003 The Bridge、wisdom 等都是合法的协作词,因为它们是产品概念,不是代码语言)
- 自然语言句子,不带括号 / 缩进 / 引号包裹

## 例外(以下场景代码语言合法)

1. 用户**明确让你落档** —— 写实际代码、改动文件、commit message
2. 用户**问具体语法 / debug** —— "这个函数报什么错"、"这一行什么意思"
3. 用户**主动用代码语言提问** —— 你回应里出现的代码语言只能是回应用户已经引入的术语,不要扩散
4. **必要的项目协作词** —— 议题号(#013)、模块名(The Bridge)、人物角色(LEAD / WORKER)— 这些是项目内的产品概念,不算代码语言

## 自检纪律

发出每段话之前问一句:**"如果剥掉所有代码壳和工程师术语,这段话还剩什么"** —— 剩下的应该已经是完整意思,而不是"剥掉就读不懂了"。

如果剥掉就读不懂 = 你在用代码语言,重写。

## 为什么这条规则物理强制

因为多次实测验证(议题 #014 v3 / #016):wisdom 软规则 + 个人偏好 + 启动 prompt 都救不了 —— 长会话里 AI 注意力漂移、被自己的工程师腔调覆盖。**只有每回合刷新一次的物理注入能稳定拉回**。

这是 议题 #003 The Bridge(人机协作)模块的物理装备。
